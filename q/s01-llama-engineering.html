模型家族／Llama 系列

使用 Llama 做微调和部署时，需要关注哪些关键问题？

追问约 5 分钟
更新于 2026-10-13
这道题接续请介绍一下 Llama 系列，Llama 1 到 3.2 有哪些主要变化？

题目

使用 Llama 做微调和部署时，需要关注哪些关键问题？

面试口述回答

我会沿着数据格式、微调策略和推理资源三条线检查。首先是 Tokenizer 和 Chat Template，Llama 2、3 的格式不同，微调和服务端必须使用对应模板，结束 token 也要正确监督和识别。复读或不停生成时，我会先从这些格式问题排查。

微调侧看 LoRA 覆盖哪些模块、秩和数据质量；显存紧张时可以用 QLoRA 保存量化基座、训练 Adapter。部署侧把权重、KV Cache 和工作区分别算，缓存公式里要使用 KV 头数，GQA 的收益就体现在这里。

最后再根据硬件和并发选择量化方案与推理引擎。如果切换到 Vision 版本，还要接好图像预处理和视觉适配器。这样从输入到生成、从训练到服务，整条链路才能保持一致。

详细知识笔记展开 / 收起

1. 先对齐 Tokenizer 和对话模板

模型训练时见过的角色边界、特殊 token 和消息顺序构成了它的输入格式。Llama 2 的 Instruct 格式包含 [INST]，Llama 3 系列使用 <|start_header_id|> 等角色标记。微调和推理都应调用对应模型的模板，保持训练输入与实际使用一致。

以 Llama 3.1 为例，<|eot_id|> 用于一轮交互结束，<|eom_id|> 用于工具交接等控制权转移，<|end_of_text|> 对应文本结束。SFT 数据需要包含正确的结束信号，推理配置需要识别这些信号。

如果模型开始复读、混入其他角色或者一直生成，可以先检查：模板是否重复套用，助手结束 token 是否参与监督，Padding 是否被正确忽略，服务端和训练端的特殊 token ID 是否一致。这比直接改采样参数更容易定位格式问题。

2. LoRA / QLoRA 怎么考虑？

LoRA 为选定线性层加入低秩增量，训练较少参数。可以先对注意力投影增加 Adapter，也可以扩展到 FFN 等线性层；覆盖更多模块会增加适配能力和训练开销。

QLoRA 将基座权重以 4-bit 等低精度形式保存，训练较高精度的低秩 Adapter，以降低微调显存。选型时可比较同一任务上的训练显存、任务效果和推理部署方式。若效果下降，可从训练数据、Adapter 覆盖模块与秩、关键计算精度等处分析。

3. Tokenizer 的变化为什么影响部署？

Llama 2 的词表约 32K，Llama 3 扩到约 128K。对代码和部分非英语文本，更丰富的词表能减少切分后的 token 数，使同一窗口容纳更多原始内容，同时减少相应的序列计算。另一方面，词表相关的 Embedding 和输出层参数也会增加。

4. KV Cache 显存怎样估算？

标准同长度 batch 下，可用

MKV≈2BLTHKVdhbM_{KV}\approx 2BLTH_{KV}d_hbMKV​≈2BLTHKV​dh​b

估算缓存字节数。BBB 为活跃序列数，LLL 为层数，TTT 为缓存长度，HKVH_{KV}HKV​ 为 KV 头数，dhd_hdh​ 为每头维度，bbb 为每元素字节数；系数 2 对应 K 和 V。

GQA 通过减少 HKVH_{KV}HKV​ 降低这部分显存。权重、KV Cache 和运行时激活应分别估算；例如 8B 权重使用每参数 2 字节，权重本身约需 16GB 十进制存储，部署还需为缓存与工作区预留空间。

5. 量化与推理引擎

AWQ、GPTQ 等方法侧重权重量化，bitsandbytes 提供低比特加载与训练相关能力。量化方案、硬件和内核需要配套，部署后可同时比较任务质量、显存、首 token 延迟和解码速度。

vLLM 的分页缓存适合多请求服务；TensorRT-LLM 可以围绕 NVIDIA 硬件优化；llama.cpp 等工具支持更广的本地运行环境。选择引擎时可从服务并发、硬件平台和运维需求出发。

6. 长文本和视觉版本

Llama 3.1 的长上下文能力依赖配套的位置频率设置与长文本训练，部署时保持模型配置一致。Llama 3.2 Vision 增加图像预处理、视觉编码器和 Cross-Attention 适配器，应用需要传入相应的图像张量与消息格式。

复习这些点时，可以沿着一条完整链路记忆：文本怎样编码—微调怎样监督—生成怎样停止—权重和缓存怎样保存—服务怎样执行。
