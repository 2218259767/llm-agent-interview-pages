RAG 中应该怎样对文本分块？

约 4 分钟
更新于 2026-10-13

题目

RAG 中应该怎样对文本分块？

面试口述回答

RAG 分块就是把长文档变成可检索、可排序、可引用的证据单元。我通常先利用标题、段落和句子边界，再按 token 预算聚合相邻句子，并保留适量重叠。块大小决定检索粒度和上下文完整性，重叠主要保住边界处的指代、条件和因果关系。比如一段材料先引用错误报道，后面再纠正，如果切块把两者分开，模型就容易只读到其中一半。每块还要保留文档和原文位置，方便追溯。选择方案时，我会先看边界有没有破坏语义，再在相同上下文预算下比较证据召回、答案质量、引用完整性和延迟，让分块服务于实际问题。

详细知识笔记展开 / 收起

分块解决什么问题？

RAG 的分块（Chunking）是把一份较长文档拆成若干可检索、可排序、可放入模型上下文的文本单元。每个块应当有清楚的主题和足够完整的语义，并带上原文位置，方便生成答案时引用。

例如一份长报告同时包含背景、实验方法和结果，直接用整份报告做检索单元会混入大量无关内容；分成合适的块之后，检索可以直接找到回答当前问题的段落。分块同时影响召回、重排、证据完整性和上下文成本。

原笔记采用的方案：先分句，再按预算聚合

原笔记演示的是三步流程：

  1. 按句子边界切分。 得到完整句子列表，再统计每句的长度。英文材料可以用句子切分器处理缩写和标点；中文及特殊领域材料按对应语言和文档结构处理。
  2. 按长度预算合并相邻句子。 顺序累加句子，接近目标块大小时在句子边界结束。标题、段落、列表和表格等结构也可以成为优先分界点。
  3. 在相邻块之间保留少量重叠。 把边界附近的句子或必要上下文带到下一个块，让指代、条件和因果关系更容易被读懂。

每个块保留文档 ID、Chunk ID、标题路径和原文范围。后续过滤、压缩和生成都沿用这些标识，答案中的证据可以回到原文。

chunk_size 和 overlap 分别控制什么？

chunk_size 控制单块大小。块较小时，主题通常更集中，检索粒度更细；需要跨句理解的问题可能要取回相邻块。块较大时，上下文更完整，同时会带入更多无关内容，增加输入成本。

overlap 控制相邻块共享的信息。合理重叠能保住边界处的条件和上下文；重叠过多会增加索引体积、重复召回和模型输入量。按完整句子保留重叠时，实际重叠长度会随句长变化，配置应明确采用“目标值”还是“硬上限”。

遇到单句超过预算，可以沿从句、标点或其他结构继续拆分，并保留必要的主语与条件。实际 token 预算采用检索模型或生成模型对应的 tokenizer。原演示用 NLTK 的词级 tokenizer 统计长度，70 和 10 是便于看清边界的演示参数。

为什么要保留句子与因果关系？

原例讲的是城市提前开闸防洪。工程师作出决定的原因是上游传感器预报第二轮洪峰即将到来，随后市中心避开了最严重的积水。报道中的“积水之后才开闸”与实际事件顺序相反。

如果在“第二轮洪峰将流向……”处截断，后半句才出现的医院区域会丢失；如果只检索到转述报道的那句，后面的纠正说明又落在另一个块，就容易误解时序。句子边界、相邻句上下文和来源位置共同帮助检索系统保留这些关系。

原演示在相同名义参数下，句子聚合得到 5 个块，固定窗口得到 3 个块；前者没有句内截断，后者出现 2 个句内分界点、3 个带破损边缘的块。这组结果直观展示了边界行为及重复内容带来的块数变化。

如何选择并评估分块方案？

先看文档类型：论文可优先利用标题与段落，FAQ 可保留完整问答，表格保留表头与行的关系。再根据问题需要的证据跨度调整块大小与重叠。

评估分两层。第一层检查结构质量，包括句内断点、缺失标题、指代不明、重复比例和原文可定位性。第二层用真实查询检查证据召回率、排序效果、回答质量和引用完整性，同时记录检索后总 token 数、延迟与索引规模。比较时控制总上下文预算，观察质量与成本的变化，再确定用于当前资料的参数。
