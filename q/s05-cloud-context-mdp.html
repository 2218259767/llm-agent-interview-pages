Agent／上下文管理与压缩

Agent 为什么需要上下文压缩？如何用状态重建的思路设计压缩？

约 5 分钟
更新于 2026-10-13

题目

Agent 为什么需要上下文压缩？如何用状态重建的思路设计压缩？

面试口述回答

Agent 的历史会随着工具调用持续增长，里面既有关键证据，也有重复和临时信息。我的设计思路是先确定下一步决策需要哪些状态，再据此压缩，比如研究目标、清单进度、已确认事实、未决问题和来源。方法上可以按块过滤、抽取带来源的事实，或者把新材料滚动合并成摘要。状态重建借用了 MDP 的思路，希望紧凑状态仍保留决定后续行为的信息；在部分可观察的工具环境中，还要记录假设、冲突和待验证项。最后我会同时测关键事实保留、任务成功率、调用行为、token 和时延，确认压缩后的状态能够支持任务继续完成。

详细知识笔记展开 / 收起

为什么长期 Agent 要压缩上下文？

多轮搜索和工具调用会不断产生网页、日志、重复结果与中间判断。随着历史增长，输入成本和处理时延增加，关键目标与证据也更难从冗长内容中被稳定使用。上下文压缩的目标是保留后续决策需要的信息，用更紧凑的表示支持任务继续进行。

可以把研究 Agent 当前需要的内容组织成“用户目标＋研究清单及完成状态＋已确认知识＋未解决问题＋来源指针”。每轮新增材料后，更新这份工作状态。

“状态重建”是什么意思？

状态是决定下一步动作所需的信息。例如研究某家公司时，下一步该查什么，取决于已经得到哪些事实、还缺哪些证据和剩余预算。把完整历史重新整理成这些字段，就是状态重建。

MDP 的马尔可夫性质描述的是：给定当前状态和动作，就能确定下一步状态与奖励的条件分布。在工程上，我们希望压缩表示尽量保留历史中影响下一步判断的信息。设历史为 hth_tht​，压缩状态为 zt=f(ht)z_t=f(h_t)zt​=f(ht​)，可以把目标写成：

P(ot+1,rt∣ht,at)≈P(ot+1,rt∣zt,at).P(o_{t+1},r_t\mid h_t,a_t) \approx P(o_{t+1},r_t\mid z_t,a_t).P(ot+1​,rt​∣ht​,at​)≈P(ot+1​,rt​∣zt​,at​).

其中 ata_tat​ 是当前动作，ot+1o_{t+1}ot+1​ 是下一次观察，rtr_trt​ 是回报。这个近似程度可以通过后续任务效果来检验。

现实工具返回的是局部观察，信息还可能缺失或冲突，因而也可以用 POMDP 理解 Agent：在部分可观察环境中，维护当前对世界的认识。理论上的 belief state 是对隐藏状态的概率分布；工程里常用事实、候选假设、冲突和待验证问题来组织这种认识。

三种常见压缩方法

方法 怎样处理内容 主要取舍
Chunk 过滤 按句子和结构切块，再依据任务选择相关块 保留原文和来源方便，但有用信息所在块可能带有冗余
事实抽取 从块中提取人物、时间、数值、关系等事实，并绑定 Chunk ID 信息更密集，提取时要保留事实条件及其来源
生成式摘要 将新材料与已有摘要滚动合并、去重并处理冲突 适合跨块综合，需核对摘要中的关键结论和遗漏

过滤适合先筛选证据，事实抽取适合组织高密度记录，摘要适合维持全局视角。系统可以根据任务阶段组合这些方法，并根据实际效果选择比例。

先定义保留标准，再运行压缩器

研究任务可以用 Checklist 指明必须回答的维度；多轮工具任务可以用状态字段指明目标、约束、候选方案、已执行动作与待确认项。压缩时保留能更新这些字段的信息，同时带上来源和时间。

例如订票场景要保存已选择的航班、价格有效期以及已经创建的订单号。对有外部写入效果的操作，执行凭证会影响下一步是否查询、修改或撤销，因此应在状态中明确记录。用户改变目标后，重新检查旧状态的相关性，并沿来源引用取回需要重新判断的细节。

怎样评价压缩质量？

同时测输入 token 的减少、关键事实覆盖、引用可追溯性、压缩耗时，以及继续执行后的成功率、重复调用和错误动作。可以在相同模型与相近预算下比较不同方法，并单独开关语义引导。

失败时沿链路定位：原始观察缺少信息、压缩过程遗漏信息，还是决策阶段没有正确使用已有信息。这样能把问题对应到检索、压缩或执行模块。
