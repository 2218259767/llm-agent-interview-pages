基础模型架构／Transformer

为什么生成式大模型普遍采用 Decoder-only 架构？

约 4 分钟
更新于 2026-10-13

题目

为什么生成式大模型普遍采用 Decoder-only 架构？

面试口述回答

主要有三个原因：任务统一、训练容易扩展、目标和生成场景一致。Decoder-only 把问答、翻译、代码和工具调用都组织为给定前缀后的下一 token 预测，所以预训练、指令微调和推理能复用同一套数据流。

它采用重复的因果 Transformer Block，训练时可以并行计算已知序列的各个位置，推理时用 KV Cache 复用历史状态，也方便做统一的系统优化。大规模数据和训练进一步增强了它的多任务生成与上下文学习能力。

我会按任务理解几种架构的分工：BERT 这类双向 Encoder 很适合分类、检索和匹配；Encoder–Decoder 适合明确的条件转换；需要统一处理多轮对话和开放式生成时，Decoder-only 的接口和训练目标尤其合适。

详细知识笔记展开 / 收起

1. 它把多种任务统一为条件生成

Decoder-only 使用因果 Transformer 堆栈，学习给定前文时下一 token 的分布：

p(x1,…,xT)=∏t=1Tp(xt∣x<t).p(x_1,\ldots,x_T)=\prod_{t=1}^{T}p(x_t\mid x_{<t}).p(x1​,…,xT​)=t=1∏T​p(xt​∣x<t​).

问答、翻译、摘要、代码和工具参数都可以写成“给定条件，继续生成”的形式。例如把“翻译成英文：我喜欢机器学习”放进前缀，再生成译文。预训练学到的续写能力可以通过指令微调转成统一的任务接口。

2. 训练流程简单，适合扩展

大规模文本本身就能提供下一 token 标签，训练时可用因果 Mask 同时计算一段序列的预测损失。预训练、SFT 和自回归推理复用同一套模型主干和序列组织方式。

从工程上看，同一种 Block 重复堆叠，便于做张量并行、流水线并行与算子优化。推理时使用 KV Cache 复用历史状态，服务系统可以围绕 Prefill、Decode 建立统一的调度机制。

3. 和另外两类架构怎样分工？

架构 如何读取条件 典型任务
Encoder-only，如 BERT 双向读取完整输入，得到上下文表示 文本分类、实体识别、向量检索、重排序
Encoder–Decoder，如 T5 Encoder 双向编码输入，Decoder 通过 Cross-Attention 条件生成 翻译、摘要、文本转换
Decoder-only 把条件放进前缀，按因果顺序生成后续内容 开放对话、通用指令、代码生成、工具调用

BERT 的 MLM 目标擅长训练双向表示，生成式应用则需要持续预测新的 token。Decoder-only 的自回归目标直接匹配这种使用方式，并且便于把任务示例、检索结果、工具说明都写入前缀。

4. 怎么理解这条路线的成功？

统一目标降低了大规模数据处理与应用适配的复杂度。随着参数、数据和训练计算增加，模型在上下文学习和多任务生成上的能力持续提升；成熟的训练与推理生态又加强了这条路线。

实际选型时，开放式多轮生成适合 Decoder-only；需要低延迟的固定标签分类或检索匹配，可以优先考虑专门的 Encoder；输入和输出分工明确的序列转换任务，也可以选择 Encoder–Decoder。用任务的信息流来解释架构，会比只背模型名称更清晰。
